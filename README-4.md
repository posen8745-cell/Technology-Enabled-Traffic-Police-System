# T 字路口科技交警模擬系統

**作者：基隆私立二信高中｜普通科數理班｜P2C29｜張博程**

> **高中自主學習作品｜上下學交通壅塞觀察｜號誌控制與車流模擬**
>
> 本系統是使用 HTML、CSS、JavaScript 製作的**互動式交通模擬**，並非實際交通號誌控制系統；未安裝或串接道路攝影機、車流感測器、號誌控制器，也未取得實際路口車流數據。模擬結果不得直接用於道路交通管制或安全決策。

## 一、作品介紹

### 自主學習動機

我家附近有一處 **T 字路口**，上下學往返時，尤其放學回家時經常遇到塞車，車輛排隊等候的情況讓我開始好奇：同樣一個路口，為什麼有時候車流順暢，有時候卻需要等很久？如果不同方向的車流量不一樣，紅綠燈秒數是否也應有所調整？

因此，我嘗試把日常觀察轉化成高中自主學習作品，先用網頁畫出 T 字路口，再模擬不同方向的車輛、紅綠燈與行人通行，讓自己能反覆調整參數、觀察排隊狀況。我也加入「科技交警」手動介入功能，示範在車流較多時延長主線綠燈，了解交通控制不只是讓某個方向多通行，也要兼顧轉彎車、行人與切換時的緩衝時間。

**重要區分：** 塞車是我在生活中觀察到的現象；系統中的車流量、等待情形與改善效果是**程式模擬**，尚未經過現地測量驗證，也不能推論家附近真實路口一定適合延長 15 秒綠燈。

### 自主學習目標

1. 理解 T 字路口的直行、轉彎、行人通行與不同號誌相位。
2. 學習使用 JavaScript 模擬車輛出現、移動、排隊和停止線判斷。
3. 比較不同號誌秒數、車流生成率與早晚模式的畫面變化。
4. 設計「科技交警」介入示範，研究主線綠燈延長與排隊變化之間的關係。
5. 練習將生活問題轉為可操作的程式作品，並認識交通控制與電機工程的連結。

## 三、模擬方式與預設參數

### 1. 車流如何產生

程式以 `spawn` 作為每秒嘗試生成車輛的機率，設定範圍為 `0～1`；例如 `0.20` 代表每秒一次的生成檢查中，約有 20% 機率新增一輛模擬車。車輛路線和速度也使用程式規則與隨機值產生。這不等於真實的「每小時車流量」調查數據。

畫面提示建議 `spawn = 0.18～0.25` 作為展示起點；當數值提高至 `0.35` 或以上時，可能出現明顯壅塞。此為模擬情境，不是實測壅塞門檻。

### 2. 三種車流配置

程式內建以下模式；其中「早上」「晚上」有手動按鈕，「平峰」作為自動判斷與初始模式使用。

| 模式 | 主線 1 直行綠 | 主線 1 轉彎綠 | 主線 2 綠燈 | 車流生成率 | 示範重點 |
| --- | ---: | ---: | ---: | ---: | --- |
| 早上（AM） | 22 秒 | 40 秒 | 34 秒 | 0.22 | 模擬主線轉彎需求偏高 |
| 平峰（MID） | 26 秒 | 28 秒 | 38 秒 | 0.20 | 模擬較均衡的車流 |
| 晚上（PM2） | 20 秒 | 28 秒 | 55 秒 | 0.22 | 模擬主線 2 通行需求偏高 |

另可自行調整黃燈與全紅緩衝時間。這些設定是程式中的**示範值**，不代表家附近路口的實際秒數或符合道路工程設計標準。

### 3. 行人時段

| 斑馬線 | WALK 預設 | CLEAR 預設 | 說明 |
| --- | ---: | ---: | --- |
| 左側 | 10 秒 | 6 秒 | 預設啟用 |
| 右側 | 10 秒 | 6 秒 | 可切換有／無 |
| 下方 | 20 秒 | 8 秒 | 預設啟用 |

`WALK` 表示開放行人通行的模擬階段，`CLEAR` 表示清空緩衝階段。程式依序處理斑馬線時段，並模擬車輛與行人的衝突限制；不是正式交通工程使用的行人時制計算。

## 四、科技交警介入原理

目前「科技交警」由使用者**手動按鈕觸發**，不是依攝影機或真實車流感測器自動介入。

```text
使用者按下「科技交警啟動（示範）」
                   │
                   ▼
    啟動車流展示（必要時提高生成率）
                   │
                   ▼
     是否為主線 1 直行綠燈相位？
          ├─ 是 → 延長該次綠燈 15 秒
          └─ 否 → 等待下一次主線 1 直行綠燈
                   │
                   ▼
      畫面顯示介入訊息與聲音提示
                   │
                   ▼
        相位結束後回到一般循環
```

介入按鈕會讓車流生成率至少提高至 `0.35`，用於製造較高需求的**展示情境**。因此，如果想比較「介入前後」的影響，必須注意它同時改變了車流生成率：**目前不能單憑畫面認定多出的 15 秒讓交通效率改善。** 若要進行較嚴謹的比較，需固定車流條件、重複測試並記錄排隊長度與等待時間。

## 五、Auto 模式的判斷概念

程式可估算停止線附近的模擬排隊車輛數，並以規則選擇模式：

- 主線 2 右轉隊列明顯較多時，偏向晚上模式（PM2）。
- 主線 1 轉彎隊列明顯較多時，偏向早上模式（AM）。
- 其他情況使用平峰模式（MID）。

程式設有排隊差距門檻，避免僅因少量變動就立即改變模式。不過，現行程式用來限制切換頻率的內部計數是在**號誌相位切換時**增加，而不是每秒增加，因此尚不能把它當成精確的「60 秒冷卻時間」。這是後續可改良的項目。

**Auto 是規則式模擬控制，不是機器學習模型，也沒有進行即時影像辨識。**

## 六、操作方法與建議展示流程

1. 開啟 [T 字路口科技交警模擬網站](https://posen8745-cell.github.io/Technology-Enabled-Traffic-Police-System/)，觀察預設的道路與紅綠燈畫面。
2. 先使用預設車流率 `0.20`，觀察各方向車輛如何產生、排隊與通過。
3. 關閉 Auto 後，分別按「早上」「晚上」，比較兩種時間配置。
4. 切換右側斑馬線的有無，觀察行人序列與車流限制。
5. 使用「Demo：高需求監測」觀察一般示範，再按「Demo：塞車介入」或「科技交警啟動（示範）」。
6. 觀察主線 1 綠燈是否延長 15 秒，以及畫面上的介入訊息、車輛排隊和行人通行狀態。
7. 使用「暫停／繼續」逐步觀察；必要時按「重置」重新開始。

**展示重點：** 建議至少比較「預設車流」「高需求但未介入」「高需求並介入」三種情境；目前網頁尚未提供正式的排隊與延誤統計報告，展示觀察應以**定性比較**為主。

## 七、程式架構與 GitHub Pages 部署

目前專案的主要 HTML、CSS 與 JavaScript 集中在 `index.html`，可由 GitHub Pages 作為靜態網頁載入；不需要安裝 Python 伺服器。

```text
Technology-Enabled-Traffic-Police-System/
├── index.html   # 路口介面、Canvas 繪圖與模擬邏輯
└── README.md    # 專案介紹與學習歷程說明
```

程式中另有 `config/intersection_I001.json` 的**設定讀取函式**，但目前首頁初始化流程並未呼叫該函式；本 README 依目前實際啟用的流程說明，不把外部 JSON 設定讀取寫成已完成的使用功能。

部署方式：

1. 將 `index.html` 與 `README.md` 放在 GitHub 儲存庫根目錄。
2. 到 **Settings → Pages**，選擇 `Deploy from a branch`、`main`、`/(root)`。
3. 部署成功後，使用網站網址測試按鈕與模擬畫面。
4. 若無法開啟，先確認 Actions 的建置／部署紀錄，不要直接推論程式損壞。

## 九、限制與後續研究方向

### 目前限制

- 模擬車流為程式隨機生成，未使用家附近路口的實測車流資料。
- 路口道路幾何、轉彎比例、號誌秒數與人行穿越情境均為示範設定。
- 科技交警是手動觸發，尚未連接 AI 攝影機、車流偵測器或交通號誌控制器。
- 介入示範會提高車流生成率，因此不能直接視為控制組與實驗組的公平比較。
- 尚未完成平均延誤、排隊長度、通過量等量化指標的長時間對照驗證。
- Auto 模式內部切換計數與變數名稱的時間單位仍有改良空間。
- 提示音及中文語音是否播放，可能受瀏覽器音訊權限和支援情況影響。

### 後續可研究的方向（尚未完成）

1. 在合法、安全且不影響交通的前提下，以**人工計數**觀察不同時段的車流與排隊情形。
2. 將車流量與號誌秒數記成表格，讓不同情境使用相同輸入條件比較。
3. 新增平均等待時間、最大排隊長度與通過車輛數等可檢驗的統計。
4. 修正 Auto 模式的時間計數方式，並為模式切換加入可追溯紀錄。
5. 研究攝影機車流辨識、感應線圈或其他感測器的原理；若涉及真實道路設備，需由主管機關與專業人員評估。
